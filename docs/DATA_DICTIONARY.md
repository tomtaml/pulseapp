# Data dictionary — prototype v0.2

The prototype is designed for **anonymous, structured workshop interaction data**. Named recruitment/contact data must remain outside this database.

## Study variants

- `fi-fleet`: Tampere / Finland — wireless charging + V2G for fleet drivers, dispatchers and fleet managers.
- `fi-citizen`: Tampere / Finland — citizen/accessibility review of the same fictional delivery-van interface. This variant measures understanding, accessibility, trust and usability without treating the participant as a fleet decision-maker.
- `uk-v2h`: Oxfordshire / UK — wireless charging + V2H alternative.

## Server-derived fields

| Field | Type | Purpose |
|---|---|---|
| `id` | UUID | Random submission identifier generated by the Worker |
| `submitted_at` | timestamp | D1 server timestamp |
| `app_version` | text | Exact prototype version tested |
| `sus_score` | real | Calculated 0–100 SUS score |
| `comprehension_score` | integer | Number of correct comprehension items |
| `trust_score` | real | Mean of structured trust items |

## Participant/session fields

| Field | Type | Notes |
|---|---|---|
| `workshop_code` | short code | Links the anonymous record to an SRF activity/session, not to an individual |
| `variant` | category | `fi-fleet`, `fi-citizen`, `uk-v2h` |
| `participant_group` | broad category | No employer or organisation name |
| `language` | `fi`/`en` | Interface/instrument language |

## Task and design-signal fields

The JSON payload can include the following structured prototype signals:

- alignment clarity (1–5);
- fictional/current battery SoC and minimum departure reserve;
- departure time used in the scenario;
- plan comprehension (1–5);
- explicit-confirmation preference for V2G/V2H;
- fault/fallback priority;
- three comprehension items;
- ten SUS responses (1–5);
- structured trust responses;
- accessibility/independent-understanding rating;
- wireless-charging acceptance (1–5);
- V2G/V2H participation/acceptability (1–5).

Free text is **off by default**. If `FREE_TEXT_ENABLED=true`, an optional note is capped at 500 characters and participants are instructed not to enter identifying information.

## Data deliberately not requested

The interface does not request:

- name;
- email or phone number;
- precise home/work address;
- employer or organisation name;
- vehicle registration/VIN/vehicle ID;
- GPS coordinates;
- account/payment information.

The Worker also strips common accidental PII field names before persistence. This is an additional safeguard, not a substitute for data minimisation and participant instructions.

## SUS language status

The English 10-item SUS wording is included in the prototype. The Finnish wording in v0.2 is a **working PULSE translation for cognitive testing**. It must be reviewed/back-translated and the final version documented before formal cross-language comparisons are made.

## SRF traceability

The workshop code and app version allow the quantitative record to be linked at activity level to the project registers:

`SRF Activity Map → Issue Response Log → Transparency Log → design requirement / indicator → later DCE or Behavioural Twin variable`

The app record itself should not contain the qualitative issue narrative, stakeholder name or design-owner contact. Those belong in the governed SRF registers.

## Data separation rule

Do not merge raw prototype records with named invitation/contact lists. Analysis tables should use only broad actor groups and activity/workshop codes unless a separately approved protocol explicitly requires otherwise.
